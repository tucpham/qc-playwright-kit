Tổng quan

Regression cần cùng input, cùng expected, kết quả lặp lại được. Một LLM thao tác trực tiếp trên app thì không deterministic: nó có thể “tự thích nghi” khi UI đổi và báo pass đúng lúc lẽ ra phải bắt được lỗi. Vì vậy MCP Playwright chỉ dùng lúc tạo hoặc sửa test.Đề bài là spec, lời giải là test, CI là người chấm.

Kit giải quyết bốn việc:

  • Chuẩn hóa. Mọi dự án dùng chung config, fixture, cách login theo role, cách tạo/dọn dữ liệu và quy ước đặt tên.
  • Truy vết. Mỗi test gắn với một test case TC-XXX-NNN trong specs/*.md, kiểm tự động.
  • Chống làm yếu test. Lint, guard và stabilize chặn wait cứng, xóa assertion, thêm skip/fixme, test flaky.
  • Đo được. Sinh metric và quality gate cho PR, nightly và release.

AGENTS.md, CLAUDE.md, ai/prompts/, .claude/commands/, .claude/agents/, .mcp.json. Chỉ dùng lúc viết hoặc sửa test: plan, generate, heal, review.

Cách hoạt động khi chạy test

Gõ npm test thì chuỗi sự kiện diễn ra như sau:

  1. Nạp config. playwright.config.ts chỉ có một dòng createConfig(project). Kit đọc .env, chọn môi trường theo TEST_ENV và dừng ngay nếu môi trường được đánh dấu isProduction.
  2. Login theo role. tests/auth.setup.ts chạy hàm login của dự án cho từng role, lấy tài khoản từ biến môi trường, lưu session vào .auth/<role>.json. Mỗi role chỉ login một lần.
  3. Test nhận fixture. Fixture role quyết định session nào được nạp (mặc định defaultRole, đổi bằng test.use({ role: 'admin' }), anonymous là chưa login). Test nhận thêm api/adminApi, Page Object, uniqueName, cleanup.
  4. Chuẩn bị dữ liệu qua API. Đăng ký cleanup trước, rồi tạo dữ liệu bằng API với tên duy nhất. Không đi qua UI để tạo điều kiện tiên quyết.
  5. Thao tác qua Page Object, assert trong test. Locator và hành động nằm trong Page Object; các expect nghiệp vụ nằm ngay trong test để reviewer thấy. Spec ghi “đã lưu” thì test kiểm thêm backend bằng expect.poll + API.
  6. Dọn dẹp và báo cáo. cleanup chạy ngược thứ tự kể cả khi test fail; lỗi dọn dẹp thành annotation chứ không che kết quả thật. Reporter sinh HTML report, results.json, junit.xml cho metrics và CI.

Một test chuẩn

import { expect, test } from '../../project/fixtures';

// Source: specs/tasks.md

test.describe('Task management', { tag: '@regression' }, () => {
  test('[TC-TASK-003] User can mark a task as done',
    async ({ tasksPage, api, adminApi, uniqueName, cleanup }) => {
      const title = uniqueName('Task');
      cleanup.add(`delete ${title}`, () => adminApi.deleteTaskByTitle(title)); // dọn trước
      const task = await api.createTask(title);                                 // tạo bằng API

      await tasksPage.open();
      await tasksPage.doneCheckbox(title).check();

      await expect(tasksPage.doneCheckbox(title)).toBeChecked();
      await expect.poll(async () => (await api.getTask(task.id))?.done).toBe(true); // kiểm backend
  });
});

Quy trình AI: plan, generate, heal, review

Chữ xanh lá: bước AI làm. Khoanh đỏ: bước bắt buộc có người.

AI được làm

  • Explore app, soạn nháp test case để người duyệt
  • Sinh code Playwright, người review rồi commit
  • Đề xuất sửa test hỏng dưới dạng PR
  • Pre-review PR test theo checklist

AI không được làm

  • Tự quyết expected result từ hành vi hiện tại của app
  • Đọc test case và tự thao tác mỗi lần chạy regression
  • Tự sửa test lúc runtime để “pass”
  • Thay người review

Heal: phân loại nguyên nhân trước khi sửa

LoạiVí dụĐược làm gì
A. UI đổi, hành vi giữ nguyênĐổi tên nút theo requirement mới đã cập nhật vào spec, đổi layoutSửa locator trong Page Object
B. Timing / flakyClick trước khi data load xongThay bằng web-first assertion, tách dữ liệu
C. Dữ liệu / môi trườngAccount test bị khóa, data cũ bị xóaSửa setup / cleanup
D. Hành vi khác specMessage sai, tính tiền sai, mất quyềnKhông sửa test. Báo bug, để test đỏ, người quyết định.

Healer mặc định của Playwright có thể tự đánh test.fixme() khi nghĩ app hỏng. Kit cấm việc này trong AGENTS.md, và npm run guard chặn nó trong CI.Loại D: để test đỏ, không fixme.

Dùng công cụ khác Claude Code

Copilot và Cursor đọc AGENTS.md. Tạo agent bằng npx playwright init-agents --loop=vscode (hoặc copilot), rồi dán nội dung prompt trong ai/prompts/. Lưu ý init-agents ghi đè .mcp.json; chạy xong cần kiểm lại.

Quality gate & CI

PhaseKhi nàoTiêu chí tự độngLệnh
Test code gateMỗi PR có đổi testTypecheck, lint, traceability, guard, test mới stabilize 5/5verify, guard, stabilize:changed
PR gateMỗi PR@smoke pass 100%, không @critical fail, flaky ≤ 5%, ≤ 10 phútmetrics -- --gate pr
NightlyHằng đêmPass ≥ 95%, không @critical fail, flaky ≤ 3%metrics -- --gate nightly
ReleaseTrước release@regression pass 100%, không @critical fail, flaky ≤ 2%, đủ coverage TC approvedmetrics -- --gate release, trace:check -- --strict

Đổi ngưỡng cho từng dự án bằng biến CI: MIN_PASS_RATE, MAX_FLAKY_RATE, MAX_DURATION_MIN.

Workflow GitHub mẫu (.github/workflows/qc-regression.yml) chạy theo ba kiểu: pull request (verify + guard + stabilize test mới + smoke), nightly lúc 02:00 giờ Việt Nam từ thứ Hai tới thứ Sáu (full regression), và chạy tay với gate tùy chọn, ví dụ release. Cần khai báo secrets tài khoản (ADMIN_USER, ADMIN_PASS…) và variable TEST_ENV.PR do guard chặn chỉ QC lead được gắn qc-approved.

Metric nằm ở metrics/latest.json, metrics/history/, metrics/traceability.json và test-results/junit.xml; gom từ artifact CI của các dự án để dựng dashboard chung.

Onboarding một dự án mới

Mục tiêu: trong 1–2 ngày, dự án có suite smoke chạy được trong CI; sau đó mở rộng dần theo test case đã duyệt.

  1. Kiểm tra điều kiện testability

    Thiếu các điều kiện này thì suite sẽ flaky. Xử lý trước, đừng cố viết test vượt qua.

    Điều kiệnMứcNếu chưa có
    Môi trường test ổn định (dev/staging), không phải productionBắt buộcĐề xuất dev/DevOps dựng
    Tài khoản test riêng cho từng roleBắt buộcXin cấp, không dùng account cá nhân
    Login tự động được (không captcha, OTP có cách bypass)Bắt buộcDev tắt captcha / cấp OTP cố định cho test account
    Tạo/xóa dữ liệu test qua API hoặc seed scriptRất nênGhi backlog dev, tạm tạo bằng UI
    Element chính có label/role rõ hoặc data-testidRất nênGhi vào app-map.md, mục Known testability gaps
    Có sẵn test case (Excel/Jira/doc)NênDùng /qc-plan để AI soạn nháp
    Làm trước khi bắt đầu.

  2. Cài kit vào repo dự án

    Giai đoạn đầu (chưa có package nội bộ), copy vào repo dự án, thường đặt trong e2e/:

    kit/  scripts/  eslint.config.mjs  tsconfig.json  playwright.config.ts
AGENTS.md  CLAUDE.md  ai/  .claude/  .mcp.json  .env.example  .gitignore
.github/workflows/qc-regression.yml   # hoặc ci/gitlab-ci.yml

    Copy làm mẫu rồi sửa: project/, specs/_TEMPLATE.md, tests/auth.setup.ts, tests/seed.spec.ts. Không copy demo-app/; xóa webServer trong project.config.ts nếu test trên môi trường đã deploy.

    npm i -D @playwright/test typescript @types/node eslint typescript-eslint eslint-plugin-playwright
npx playwright install chromium

    Khi kit đã thành package nội bộ: npm i -D @company/qc-playwright-kit và đổi import '../kit' thành '@company/qc-playwright-kit'.

    ~30 phút

  3. Điền project adapter

    1. project/project.config.ts: tên dự án, môi trường (đánh isProduction: true cho prod), role và tên biến env chứa tài khoản.
    2. project/login.ts: các bước login, kết thúc bằng một expect chứng minh đã vào app.
    3. .env (local) và secrets trên CI: tài khoản từng role.
    4. project/api.ts: client tạo/dọn dữ liệu.
    5. project/pages/: 1–2 Page Object cho màn hình chính, đăng ký vào project/fixtures.ts.
    6. tests/seed.spec.ts: mở màn hình chính sau khi login.
    7. project/app-map.md: màn hình, URL, role, flow chính.
    // project/project.config.ts (rút gọn)
export default defineProject({
  name: 'orders',
  environments: {
    staging:    { baseURL: 'https://staging.example.internal' },
    production: { baseURL: 'https://app.example.com', isProduction: true },
  },
  defaultEnv: 'staging',
  roles: {
    admin: { usernameEnv: 'ADMIN_USER', passwordEnv: 'ADMIN_PASS' },
    user:  { usernameEnv: 'USER_USER',  passwordEnv: 'USER_PASS' },
  },
  defaultRole: 'user',
  login,
});

    Kiểm tra: npx playwright test tests/seed.spec.ts xanh là adapter đã đúng.

    ~1–2 giờ

  4. Chuẩn bị test case

    • Có Excel/CSV: npm run tc:import -- testcases.csv orders --feature ORD, rồi /qc-import để AI làm sạch.
    • Chưa có: /qc-plan "Quản lý đơn hàng" <link requirement> để AI explore và soạn nháp.
    • QC/BA review specs/<feature>.md: sửa expected, giải quyết các mục [NEEDS CONFIRMATION], đổi Status: approved cho case đã chốt.

    Expected result phải lấy từ requirement, không lấy từ “app đang chạy ra sao”. Đây là chỗ AI dễ sai nhất.

    0.5–1 ngày mỗi feature

  5. Generate test

    /qc-generate specs/orders.md TC-ORD-001,TC-ORD-002

    Bắt đầu với 3–5 case P1 để kiểm chứng adapter và Page Object, rồi mới generate hàng loạt.

  6. Stabilize và verify

    npm run stabilize -- tests/regression/orders.spec.ts   # 5/5 xanh, không retry
npm run verify                                          # typecheck + lint + traceability

  7. Review

    Reviewer dùng docs/04-review-checklist.md; có thể chạy /qc-review để AI review trước. Trọng tâm: assertion có kiểm đúng nghiệp vụ trong spec không, và test có đỏ khi tính năng hỏng không.

  8. Đưa vào CI

    • Copy workflow, khai báo secrets (ADMIN_USER…) và variable TEST_ENV.
    • PR: verify + guard + stabilize test mới + smoke. Nightly: full regression. Trước release: chạy tay với gate release.
    • Tạo label qc-approved (chỉ QC lead được gắn) để duyệt các thay đổi bị guard chặn.
    1–2 giờ

  9. Bảo trì

    • Test fail: /qc-heal <test>. AI chỉ được sửa loại A, B, C; loại D thì báo bug, không sửa test.
    • Nâng Playwright: npm i -D @playwright/test@latest && npm run agents:init, rồi kiểm lại .mcp.json.
    • Nâng kit: theo CHANGELOG.md (semver: PATCH sửa lỗi, MINOR thêm helper/rule, MAJOR đổi API).
    • Gom testability gaps gửi dev mỗi sprint; giữ app-map.md luôn cập nhật.

Quy tắc không được vi phạm

Tóm tắt từ AGENTS.md, áp dụng cho cả người và AI.

  • Không sửa file trong kit/. Thiếu gì thì đề xuất với QC.
  • Không “cập nhật” expected cho khớp với app. Expected chỉ lấy từ specs/*.md.
  • Không sinh test cho TC chưa approved. Mỗi TC là một test, title [TC-XXX-NNN] <title trong spec>.
  • Không làm yếu assertion: không xóa expect, không đổi so khớp chính xác thành một phần, không .or(), không tăng timeout, không { force: true }.
  • Không tự thêm test.skip, fixme, only, fail. App có vẻ hỏng thì báo bug, người quyết định.
  • Không waitForTimeout, waitForSelector, networkidle, XPath, chuỗi CSS dài.
  • Không chạy trên môi trường isProduction.
  • Không để credential, token, dữ liệu cá nhân trong code, spec hay commit message.

Và hai thói quen luôn làm:

  • Locator theo thứ tự getByRole → getByLabel → getByPlaceholder → getByText → getByTestId.
  • Dữ liệu tạo qua API, tên dùng uniqueName(), đăng ký cleanup trước khi tạo, không phụ thuộc test khác hay tổng số bản ghi.
